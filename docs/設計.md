## 0. このアプリが何をしないか

作るものを決めるより、**作らないものを決める**ほうが効いている。

| しないこと | 理由 |
|---|---|
| **OAuth トークンを自分でリフレッシュしない** | 失敗すると Claude Code 本体のセッションが壊れる。数字が出ないより遥かに困る |
| **`~/.claude` に書き込まない** | 本体のデータ。読むだけ |
| **未文書化のシェル API を使わない** | タスクバーへの埋め込みや Deskband は Windows Update で壊れる |
| **しきい値を自前で決めない** | サーバーの `severity` に従う。公式 UI と食い違わせない |
| **設定画面を作らない** | 個人用ツールに見合わない。よく使うものだけメニューに出す |
| **ログライブラリを入れない** | 70 行で足りる。常駐アプリの依存は少ないほどよい |
| **UI を殺せる設定を置かない** | パネルを隠せるようにすると、メニューに辿り着けず終了もできなくなる |
| **通知を出さない**（2026-09-23 決定） | **常に画面に出ているものを、さらに通知する意味が薄い。** トレイ廃止で手段も失っており、取り戻すには方針に逆行するか重い仕組みが要る。見逃しが実際に困ってから考える |
| **ローカル JSONL を集計しない**（当面。2026-09-23 決定） | トークン数とコストは既にターミナルの statusline で見えている。**同じものを 2 箇所で計算すると、食い違ったときにどちらが正しいか分からなくなる。** パネルは「リミット消費率」に絞る |

**被害の非対称性**がすべての判断の軸になっている。このツールが動かなくても
「使用量が分からない」だけだが、本体を壊すと仕事が止まる。
迷ったら本体に触らないほうを選ぶ。

## 1. ゴールと確定した方針

| 項目 | 決定 |
|---|---|
| **プラットフォーム** | Windows 11。実装言語は **C# / .NET 9**（優先度 C# > TypeScript > その他、のユーザー指定に従う） |
| **表示方式** | **デスクトップ上の最前面パネルを常駐**。通知領域（トレイ）は廃止、タスクバー直描きは不採用（2 章） |
| **表示したい指標** | ① 5 時間リミット% ② 週次リミット% ③ 累計トークン/コスト ④ 現在セッションの消費 ⑤ **Fable などモデル別の使用量**（ユーザー確定・全部） |
| **データ取得** | `GET /api/oauth/usage`（Claude Code 本体が使う内部 API・実測で HTTP 200 確認済み）＋ ローカル JSONL 解析 |
| **成果物** | **新規の独立リポジトリ** `ClaudeUsageTray`。本ドキュメントは設計の正本 |
| **絶対にやらないこと** | **自前での OAuth トークンリフレッシュ**（4-2 参照） |

### 段階リリースの方針

小さく動くものを先に出し、独立に足していく。実際、**Phase 1（5 時間% が数字で出る）の時点で毎日使える状態**になった。

### ✅ 現在できていること（2026-09-21）

```
5h 35% 3:13  │  週 89% 7:03  │  Fable 0% 7:03
```

- 5 時間 / 週次 / モデル別の消費率と、リセットまでの残り時間
- サーバーの `severity` に追従した色分け（青 → 琥珀 → 赤）
- ドラッグで移動・位置記憶（マルチモニタ対応）・クリック透過の切り替え
- 全画面アプリ実行中の自動退避
- Windows 起動時の自動起動（`--install`）

**残っているのは主に堅牢化（Phase 2）とローカル JSONL 集計（Phase 4）。**

## 2. Windows の物理制約（macOS との決定的な差）

### 2-1. ★★ Windows の通知領域に「テキストラベル」は存在しない（トレイ廃止の理由）

macOS の `NSStatusItem.button.title` は**可変幅のテキスト**をメニューバーに置ける。Windows の通知領域が受け付けるのは `Shell_NotifyIcon` に渡す **論理 16×16 の正方形 HICON 1 枚だけ**。

→ 16px に読める形で入るのは実質 **2〜4 文字**。「42%」は実績あり（Core Temp が全コア温度を数値でトレイ表示している）。**「1.2M tok」のような 8 文字は 1 枚のアイコンには物理的に入らない**。

さらに **Windows 11 は新規のトレイアイコンを既定でオーバーフロー（∧）に隠す**（7-7）。

この 2 つを合わせると、トレイ方式は次のようになる。

| | macOS メニューバー | Windows 通知領域 |
|---|---|---|
| 置けるもの | 可変幅のテキスト | **16×16 のアイコン 1 枚** |
| 既定の可視性 | 常に見える | **既定で隠れる** |
| 5 指標の同時表示 | できる | **できない**（2〜3 文字） |
| 状態確認 | 見るだけ | **クリックが要る** |

→ **「常に見えていてほしい」という元の要求と正反対**になる。実機で確認したうえでトレイを廃止した。

代わりに採用したのが **デスクトップ上の最前面パネル**。文字数の制約が無く、値を横に並べるだけで済む。使うのは `Form` と拡張スタイルという枯れた公開 API だけ。

```
WS_EX_LAYERED      半透明にする
WS_EX_TRANSPARENT  クリックを下へ素通りさせる（既定では付けない）
WS_EX_TOOLWINDOW   Alt+Tab とタスクバーに出さない
WS_EX_NOACTIVATE   クリックしてもフォーカスを奪わない
```

> ### ⚠ 実装で踏んだ罠: `WS_EX_TRANSPARENT` は `CreateParams` に含めること
>
> `SetWindowLongPtr` で後付けするだけでは足りない。**`Opacity` を変えると WinForms が `CreateParams` から拡張スタイルを作り直してフラグを消す。** 移動モードを抜けたあとクリック透過が復帰しない、という形で表面化した。

### 2-2. タスクバーへの直接描画は全滅

| 方式 | 判定 | 理由 |
|---|---|---|
| Deskband (COM `IDeskBand`) | ❌ | Win7 以降非推奨、**Win11 の XAML タスクバーは非対応** |
| デスクトップツールバー (Toolbars) | ❌ | **Win11 で機能自体が削除済み** |
| タスクバーへ子ウィンドウ埋め込み（`SetParent` / TrafficMonitor 方式） | ❌ | 未文書化 API。24H2/25H2 でウィジェットと重なる位置ずれ issue が継続。セキュリティソフトに注入をブロックされる |
| ExplorerPatcher / StartAllBack 依存 | ❌ | 25H2 でスタートメニュー不整合・Windows Update がブロックされた事例 |
| Windows 11 ウィジェットボード | ❌ | **ボードを開いた時しか見えない**＝常時表示の要件を満たさない |
| `ITaskbarList3::SetOverlayIcon` | ❌ | 結局 16×16。かつタスクバーボタンが存在し続ける必要がある（劣化版） |
| 通知領域アイコン（動的描画） | ⚠ **一度採用し、実機で却下** | API の安定性は確かに最高（全部公開 API）。だが 2-1 のとおり**要求を満たせなかった** |
| **デスクトップ上の最前面パネル** | ✅ **採用** | 16px の文字数制約が無い唯一の「壊れない」方式。全部公開 API |

### 2-3. TypeScript 案が Windows では成立しない

| | Electron | Tauri v2 |
|---|---|---|
| バンドル | 80〜200MB | 3〜10MB |
| アイドルメモリ | ~168MB | ~42MB |
| 動的な数値アイコン | **`tray.setTitle()` は macOS 専用**。Windows では canvas→ICO 変換を自前実装 | `set_icon(Image)` はあるが**画像生成コードは Rust 側**に書くことになる |

→ **mac で 1 行だった `setTitle()` が Windows では丸ごと消える**ため、「クロスプラットフォームで書ける」というメリットがまさにこの機能で失われる。Tauri は結局 Rust を書く。**C# が最短かつ一貫している。**

## 3. データ取得（本件の核心）

### 3-1. ★ 主データ源: `/api/oauth/usage`（実測で HTTP 200 確認済み）

```
GET https://api.anthropic.com/api/oauth/usage
  Authorization: Bearer <accessToken>
  anthropic-beta: oauth-2025-04-20
  User-Agent: claude-cli/2.1.278 (external, cli)
  Accept: application/json
  timeout 5s
```

Claude Code 本体（`claude.exe` v2.1.278）が `/usage` スラッシュコマンド・VS Code の usage パネル・statusLine の `rate_limits` を描画するために叩いている**内部エンドポイント**。バイナリ内に以下の定義を確認:

```js
{ plain: "/api/oauth/usage",
  at_wall: "/api/oauth/usage?at_wall=1&skip_spend=1",
  cedar_ember: "/api/oauth/usage?cedar_ember=1&skip_spend=1" }
```

### ★ `limits[]` が唯一の分類ソース

```json
"limits": [
  { "kind": "session",       "group": "session", "percent": 4,  "severity": "normal",  "resets_at": "...", "scope": null, "is_active": false },
  { "kind": "weekly_all",    "group": "weekly",  "percent": 84, "severity": "warning", "resets_at": "...", "scope": null, "is_active": true },
  { "kind": "weekly_scoped", "group": "weekly",  "percent": 0,  "severity": "normal",  "resets_at": "...",
    "scope": { "model": { "id": null, "display_name": "Fable" } }, "is_active": false }
]
```

→ **要望 5 指標のうち ①5 時間% ②週次% ⑤モデル別（Fable）が、この 1 リクエストで全部取れる。**

内部スキーマに *"Classify a row on this, never on a label."*（行の分類は `kind` で行え、ラベルで分類するな）と明記されている。レスポンスには `nimbus_quill` / `cinder_cove` / `tangelo` / `harbor_lantern` 等の**コードネーム付きウィンドウが多数あり大半は null**。これらを名前で解釈しようとしないこと。

全スキーマが `.passthrough()` なので**未知フィールドが増えても壊れない**。C# 側も未知プロパティを無視する設定にしておけば同様に耐える。

### ⚠ `severity` は自前しきい値を作らずサーバー値をそのまま使う

`normal` / `warning` / … がサーバーから来る。自前で 80%/90% のしきい値を決めると**公式 UI と表示が食い違う**のが最悪。色分けも通知トリガもこの値に従う。

### 3-2. 他の取得方法との比較

| # | 方法 | 取得できる値 | 認証 | 判定 |
|---|---|---|---|---|
| **A** | **`/api/oauth/usage`** | 5h%・週次%・モデル別%・`resets_at`・追加クレジット・spend | `.credentials.json` の OAuth Bearer | ✅ **採用** |
| B | statusLine フック | A と同じ `rate_limits` ＋ セッションコスト・コンテキスト窓 | 不要 | △ **対話セッション起動中しか動かない**。フォールバックとして Phase 7 |
| C | ローカル JSONL 解析 | トークン数・コスト概算 | 不要 | ✅ 補助として採用。**リミット% は出せない** |
| D | OpenTelemetry | `claude_code.token.usage` / `cost.usage` | 不要 | ❌ Collector が必要で過剰。リミット%なし |
| E | claude.ai Web API (`/api/organizations/{orgId}/usage`) | A とほぼ同じ | `sessionKey` Cookie | ❌ Cloudflare WAF に弾かれる報告多数、TTL 30 日 |
| F | Admin API (`/v1/organizations/usage_report/messages`) | 組織の API 消費のトークン数・コスト | **Admin API キー**（別物） | ❌ **サブスクのリミット% とは無関係**。レスポンスにレート制限窓の概念が無い |
| G | `claude auth status --json` | ログイン状態・プラン種別のみ | 不要 | ❌ 使用量は含まれない |

**`claude usage` サブコマンドは存在しない**（`claude --help` 全文を実測で確認）。`/usage` は対話セッション内のスラッシュコマンド専用で `--print` から呼べない。

### 3-3. ⚠ リミットの残量はローカルだけでは原理的に出せない

リミットの**分母**（そのプラン・ティアで許される量）はサーバー側にしかない。`.credentials.json` に `rateLimitTier` という文字列はあるが、これは識別子であって数値ではない。

ccusage / Claude-Code-Usage-Monitor が **P90（過去実績の 90 パーセンタイル）推定**に頼っているのはこのため。

Anthropic 自身も statusLine スキーマの `behaviors: { day, week }` を *"What's contributing to limits usage, from a scan of local transcripts on this machine"* と定義しており、**「ローカル transcript は内訳の説明用、% はサーバーから」**という切り分けをしている。本設計もこれに従う。

## 4. 認証の扱い

### 4-1. `.credentials.json` を毎ポーリングで読み直す

`%USERPROFILE%\.claude\.credentials.json`:

```json
{ "claudeAiOauth": {
    "accessToken": "...", "refreshToken": "...",
    "expiresAt": 1789985370385,            // ★ epoch ミリ秒
    "refreshTokenExpiresAt": 1792133003385,
    "subscriptionType": "team", "rateLimitTier": "..." },
  "trustedDeviceToken": "..." }
```

実測: `accessToken` の残寿命は **約 4.7 時間**、`refreshToken` は **約 25 日**。

→ 数分おきにポーリングする常駐アプリでは**アクセストークンが 4〜8 時間で必ず失効する**。対処は「毎回ファイルを読み直す」。Claude Code 本体が動いていればトークンを自動更新して書き戻すので、それに追従する。

### 4-2. ★★ 自前リフレッシュは絶対に実装しない

`POST https://platform.claude.com/v1/oauth/token` で自前リフレッシュは技術的には可能（public client、secret 不要）。**しかし実装しない。**

- リフレッシュのレート制限（4 時間に 1 回で 429）
- Cloudflare WAF ブロックの既知バグ
- **自前リフレッシュで Claude Code 本体のセッションを壊すリスク**

→ **壊れたときの被害（Claude Code が使えなくなる）が、このツールの便益を大きく上回る。** これは設計上の固い制約としてコードコメントにも書く。

関連 issue: anthropics/claude-code#38248 / #47754 / #53063

### 4-3. ⚠ ファイル読み取りは `FileShare.ReadWrite | FileShare.Delete` 必須

`FileShare.Read` だけで開くと、**こちらが Claude Code 本体のトークン書き戻しをブロックしてしまう**。これが最悪のシナリオ。

`IOException` は 120ms × 3 回リトライ。JSON が不正なら**前回のトークンを使い続ける**（書き込み途中を掴んだだけの可能性が高い）。

### 4-4. トークンの露出を抑える

`SecureString` は .NET Core 以降 Microsoft 自身が非推奨としているので使わない。代わりに:

1. **保持しない** — `PollingService` はトークンをフィールドに持たず、比較用に `SHA256(token)` の先頭 8 バイトのみ保持
2. **`DefaultRequestHeaders` に入れない** — `HttpRequestMessage` に毎回セット
3. **ログに出さない** — `Log.Write` の内部で `Redact()` を強制適用（呼び出し側の意識に依存させない）
4. **例外を素通ししない** — UI とログには `ex.GetType().Name + SafeShortMessage(ex)` のみ

## 5. ★ ローカル JSONL の実測で判明した落とし穴

### 5-1. ★★ 同一 usage が複数行に重複する（未対応だと約 2 倍ずれる）

実測（`9d058499-...jsonl` / 8.7MB / 2,102 行）:

- `type:"assistant"` の行 = **570**
- ユニークな `requestId` = **287**

同一 requestId の 2 行は `uuid` だけが違い、`message.id` と usage は**完全に同一**:

```
requestId=req_011CfCq3iiYmY8dG4pyVxczS  (2行)
  msgId=msg_011CfCq3jCLFxaQ4gKqDz3xv uuid=0b86a2ec in=2 cc=45112 cr=0 out=137 ts=...12:52:03
  msgId=msg_011CfCq3jCLFxaQ4gKqDz3xv uuid=3941e7ef in=2 cc=45112 cr=0 out=137 ts=...12:52:04
```

→ **dedup キーは `message.id` → `requestId` → `uuid` の優先順**。ccusage が `requestId + message.id` をキーにしているのはこのため。

> ✅ **既存実装と独立に一致した**。[`claude-code-statusline.md`](../../ideas/work/claude-code-statusline.md) が同じ現象を別途実測しており、数字も一致する（単純合計 570 行 244,220,933 → `requestId` 重複排除 287 行 **123,093,271**）。
>
> ★ さらに有用な知見として、**重複は必ず連続して現れる**（実測 3 ファイルで非連続の重複 0 件）。
> → **全 ID の `HashSet` を持つ必要はなく、直前の `requestId` を 1 つ覚えておくだけで排除できる。** 本アプリもこの簡略版を採用し、`_seenIds` の永続化設計（11-2）は不要になる。ただし増分 tail と組み合わせるため、**「前回読み終えた最後の requestId」だけはカーソルと一緒に永続化**すること。

### 5-2. ★ `apiBlockIndex` は 5 時間ブロックではない

名前から誤解しやすいが、実測で否定された:

```
block 0  count 287  from 2026-09-19T12:52:03Z  to 2026-09-21T03:00:34Z
block 1  count 162  from 2026-09-19T12:52:04Z  to 2026-09-21T02:59:50Z
block 2  count 114  from 2026-09-19T12:52:40Z  to 2026-09-21T02:52:35Z
```

**全ブロックが同じ秒に開始し、時間範囲が完全に重なっている。** 5 時間ウィンドウの算出には使えない。

正体は **1 レスポンス内の content block のインデックス**。1 回の API レスポンスが複数の content block を持つと、同じ `usage` を載せた行が **ブロック数だけ**書かれ、`requestId` は同じまま `apiBlockIndex` が 0,1,2... と振られる（5-1 の重複の正体がこれ）。

→ 5h ブロックは ccusage 方式（UTC 基準、前ブロック終了後のターンで `floor(timestamp, 1時間)` を開始点に新ブロックを開き 5h で閉じる）で自前算出する。

### 5-3. サブエージェントのログは別ディレクトリ（重複はしない）

```
projects/<proj>/<sessionId>.jsonl                        ← メイン
projects/<proj>/<sessionId>/subagents/agent-XXXX.jsonl   ← サブエージェント（最大 6.7MB）
```

メインとサブの requestId 集合の**重なりは 0 件**。完全に別枠の実消費なので `SearchOption.AllDirectories` で**再帰列挙が必須**。逆に言えば重複カウントの心配はない。

### 5-4. `usage.iterations[]` を足すと二重計上

```json
"usage": { "input_tokens":2, "cache_creation_input_tokens":12445, "cache_read_input_tokens":33025,
  "output_tokens":1661, "output_tokens_details":{"thinking_tokens":1133},
  "cache_creation":{"ephemeral_1h_input_tokens":12445,"ephemeral_5m_input_tokens":0},
  "iterations":[ { ... } ],        // ← トップレベル usage の内訳。足すな
  "service_tier":"standard", "speed":"standard" }
```

`Utf8JsonReader` で `iterations` に来たら `reader.Skip()` する。

### 5-5. ★ `cache_read` を別単価で計算しないと約 10 倍ずれる

実測（1 セッション・2026-09-19〜09-21・assistant 570 件）:

```
input = 1,140 / output = 893,269 / cache_creation = 6,383,986 / cache_read = 236,942,538
```

**cache_read が圧倒的多数。** 通常入力単価で誤計算すると 1 桁違う金額になる。

`cache_creation_input_tokens` は `cache_creation.{ephemeral_1h, ephemeral_5m}` の合計と一致する（実測: `cc=12445, 1h=12445, 5m=0`）。**内訳があれば内訳を使い、無い場合のみ 5m 単価で計上**する。

> ⚠ **各モデルの単価の実数値は本ドキュメントでは未確定。** 実装時に公式ドキュメントから input / output / cache write(5m,1h) / cache read を取得すること。`cache/model-catalog/*.json` に価格フィールドは **0 件**（grep で確認済み）なので、ハードコード ＋ `pricing.json` での上書きしか手がない。

**未知モデルを黙って 0 円にしない。** `unknown` バケットに集計して「未計上: `<model>` / N トークン」と赤字表示する（黙って 0 にすると「安いな」と誤解して危険）。

### 5-6. ✅ アクティブセッションは推測不要（公式のレジストリがある）

`~/.claude/sessions/<pid>.json`（数百バイト）:

```json
{"pid":14984,"sessionId":"62ae6e1d-...","cwd":"<プロジェクトの作業ディレクトリ>",
 "startedAt":1789967877059,"version":"2.1.278","kind":"interactive","entrypoint":"cli",
 "name":"ideas-af","status":"busy","updatedAt":1789968673242}
```

**プロセスごとに 1 ファイル**なので複数の Claude Code が同時起動していても全部拾える。`version` は User-Agent の自動追従にも使える。

`sessionId` → JSONL パスの逆引きは、**`cwd` からディレクトリ名を自前変換せず `projects/**/<sessionId>.jsonl` をファイル名一致で再帰検索する**。実測の `F--old-d-drive--F---work-ideas` のように非 ASCII の `■F` が `-` に潰れ `_` も `-` になる複雑な規則を推測するのはリスクが高い。

### 5-7. ✅ 走査コストは安い（設計をシンプルにできる）

- `~/.claude/projects` 全体 = **42MB**
- 8.7MB / 2,102 行のファイルを `[IO.File]::ReadLines` + `string.Contains` で **73ms**

→ **「全走査は重い」という前提は覆る。** 起動時フル走査（8 日フィルタ付き）は 1 秒未満で終わる。複雑な機構は不要。

### 5-8. ❌ `stats-cache.json` はフォールバック源として使えない

`lastComputedDate: "2026-01-24"` で **8 ヶ月止まっている**（`totalSessions: 4`、`costUSD` は 0 のまま）。`history.jsonl` はプロンプト文字列のみでトークン数を含まない。`policy-limits.json` はコンプライアンス設定で使用量とは無関係。

>

### 7-1. テキストの組み立て

「文字列 + 色」のセグメントの並びとして組み、左から順に描く。

```
5h 35% 3:13  │  週 89% 7:03  │  Fable 0% 7:03
└┬┘ └┬─┘ └┬─┘     └┬┘ └┬─┘         └─┬──┘
 │   │    │        │   │             └ weekly_scoped は返ってきた分だけ並べる
 │   │    │        │   └ severity 色
 │   │    │        └ ラベルは淡色
 │   │    └ リセットまでの残り（1 秒ごとに更新）
 │   └ severity 色（青 → 琥珀 → 赤）
 └ ラベルは淡色
```

モデル名はハードコードせず `scope.model.display_name` をそのまま使う。

### 7-2. ⚠ 文字の描画で踏んだ罠 2 つ

**① `TextRenderer`(GDI) は使えない。**

当初「16px の可読性のため GDI の `TextRenderer.DrawText` を使う」と設計していたが、
**GDI はアルファチャンネルを書かない**。32bpp ARGB に描くと文字のピクセルが
α=0 のまま残り、アイコン化したときに文字が透明で消える。
（トレイをやめた今も、パネルは半透明なので同じ問題に当たる）

正解は **GDI+ の `Graphics.DrawString`**。`TextRenderingHint` はそもそも GDI+ 側の
設定であって `TextRenderer` には効かない、という点も当初の記述が誤っていた。

**② `GenericTypographic` は末尾の空白を幅に数えない。**

セグメントを連結して描くとき、`MeasureString` が末尾の空白を無視するため
次のセグメントが詰まり `5h35%` のようにくっつく。
`StringFormatFlags.MeasureTrailingSpaces` を付けること。

### 7-3. 配色

| severity | 色 | 備考 |
|---|---|---|
| normal | `#6FB4EC` 青 | |
| warning | `#F0A830` 琥珀 | |
| critical | `#F06A6E` 赤 | |

パネルの背景は常に暗い（`#121214` 相当・不透明度 0.82）ので、テーマ判定は不要。

### 7-4. 操作設計

当初はクリック透過を既定 ON にしていた。作業の邪魔をしないという意味では
正しいが、**透過していると掴めないので移動もメニューも開けず**、入口が
グローバルホットキーだけになって「動かせないアプリ」になった。

→ **既定は透過 OFF。** 掴めること・右クリックでメニューが出ることを優先する。
画面の隅の小さなパネルなので、クリックを奪う害は小さい。

| 操作 | 効果 |
|---|---|
| ドラッグ | 移動（離した時点で位置を保存） |
| 右クリック | メニュー |
| `Ctrl+Shift+U` | 移動モード。透過 ON のときでも掴めるようにする |

ホバー時に薄い枠と左端のグリップ（点 6 個）を描き、掴めることを視覚的に示す。

### 7-5. ★ 位置の保存は相対座標で

**絶対座標で保存してはいけない。** 解像度変更やモニタの抜き差しで画面外に飛び、
クリック透過と相まって二度と掴めなくなる。

保存するのは **モニタのデバイス名 + 作業領域に対する相対座標 (0.0〜1.0)**。
復元時は作業領域内へクランプし、該当モニタが無ければプライマリへフォールバック。

> ### ✅ 実機で効果を確認（3 画面環境）
>
> 検証環境は 3 枚構成だった:
>
> ```
> DISPLAY2 (primary)  0,0      - 1920,1080
> DISPLAY1            1926,-621 - 3846,459     ← 右上
> DISPLAY3            1920,459  - 3840,1539    ← 右下

>
> DISPLAY1 の右上に置いた位置が、**アプリの再起動と実行ファイルの
> 配置先変更（publish → %LOCALAPPDATA%）をまたいで正しく復元された**。
>
> ⚠ 同時に調査上の教訓もあった。動作確認のスクリーンショットを

> パネルを「消えている」と誤判定した**。マルチモニタ環境では
> `SystemInformation.VirtualScreen` で撮るか、ウィンドウ矩形を直接問い合わせること。

`SHQueryUserNotificationState` でシェルの状態を聞き、

前景ウィンドウの矩形とモニタ矩形を比べる自前判定もできるが、シェルが持っている

## 8. ポーリング設計

> ### ⚠ この章の 8-1〜8-4 は大半が「設計であって実装ではない」
>
> 実装済みは **8-1 の上 2 行と、自動起動時の初回遅延、タイムアウトの扱いだけ**。
> 残りは Phase 2 の予定であって、いま動いてはいない（16 章の懸念 2〜5）。
> 印を付けずに書くと「対応済み」に読めてしまうため、各表に実装列を置いてある。

### 8-1. 間隔

| 状態 | 間隔 | 実装 |
|---|---|---|
| 通常 | **120 秒**（`--interval` で変更可。**下限 60 秒でハードクランプ**） | ✅ |
| ジッタ | ±10% | ✅ |
| 自動起動（`--startup`）直後 | 初回取得を **15 秒**遅らせる。ログオン直後は I/O が混み、本体もまだ起動していない | ✅ |
| **スリープ復帰 / ロック解除 / ネットワーク復帰** | **即時 1 回**（`WakeSignals`） | ✅ |
| 失効中（送らない周期） | 通常間隔のまま。バックオフを持ち越さない | ✅ |
| Claude Code が 1 つも起動していない | 600 秒に落とす（**止めはしない**） | ✅ |
| 認証エラー継続中 | 300 秒 | ⬜ |

> ### ★ 起床シグナルは「起こす」だけで「止める」ことには使わない
>
> `NetworkInterface.GetIsNetworkAvailable()` は**信用できない**。VPN アダプタ、
> Hyper-V の仮想スイッチ、WSL の仮想 NIC が「接続あり」を返すので、実際には
> 繋がらないのに `true` になる。逆もある。
>
> **これで送信を抑制すると、繋がるのに沈黙するアプリになる。**
> しかも理由は画面に出ない。`expiresAt` を時計と突き合わせて永久に黙る危険と
> まったく同じ構図で、逃げ道をまた 1 つ作る羽目になる。
>
> だから**起床のきっかけとしてだけ**使う。誤検出しても「余計に 1 回取りに行く」
> で済み、新しい失敗モードを作らない。
>
> ### これがあるから、バックオフの上限を伸ばせた（600 秒 → 30 分）
>
> 上限が 600 秒で止まっていたのは、**復帰に気づく手段がポーリングしかなかった**から。
> 長くするとその分だけ復帰が遅れる。起床シグナルがあれば復帰は数秒で拾えるので、
> 上限を伸ばしても体感は悪くならない。
>
> | 8 時間オフラインのとき | 試行回数 | 復帰までの遅れ |
> |---|---|---|
> | バックオフ無し（実測） | **233 回** | 最大 2 分 |
> | バックオフのみ（上限 600 秒） | 約 50 回 | 最大 10 分 |
> | **起床シグナル + 上限 30 分** | **約 16 回** | **数秒** |
>
> **回数と復帰速度が同時に良くなる。** なお `NetworkAddressChanged` はアダプタ
> ごとに何度も飛ぶので 10 秒で間引き、さらに送信間隔の下限（8-4）が
> `UsageEndpointClient` にあるので、間引きを抜けても 60 秒より速くは飛ばない。

**60 秒未満は設定でも許可しない。** Claude Code 本体がキャッシュ実装で `h0t = 60000`（60 秒）のスロットルをかけており、チェンジログにも「editor windows and non-interactive sessions on one machine now share a read made in the last minute instead of each calling the usage endpoint」とある。**本体より速く叩くのは礼儀違反かつ 429 リスク。**

### 8-2. `resets_at` 前倒しトリガ ⬜ 未実装

`resets_at + 3 秒` が次回定期より早ければそちらを採用。**同じ `resets_at` に対して 1 回まで**（サーバーが `resets_at` を更新し損ねていると無限ループするのでガード必須）。

実装は `PeriodicTimer` ではなく **`Task.Delay(next - now, ct)` ループ**（`PeriodicTimer` は間隔を動的に変えられない）。

### 8-3. 401 フロー △ 一部実装（16 章の懸念 5）

> ### ★ そもそも 401 を受けに行かない
>
> ShortWatch を書く前に、もっと手前に答えがあった。
> **`.credentials.json` には `expiresAt` がある。失効は送る前に分かる。**
> 「送ってみて 401 で確かめる」必要がそもそも無い。
>
> ```
> 送信前に Credentials.IsExpired を見る
>   ├ 失効している → 送らない。AuthRequired のまま次の周期で読み直す
>   └ 生きている   → 送る
> ```
>
> これで PC 再起動直後のリクエストは **7 回 → 0 回**になる。
>
> ⚠ **`expiresAt` は端末の時計と突き合わせる絶対時刻**なので、時計が大きく
> ずれていると生きているトークンを失効と誤判定しうる。その場合に「送らない」
> だけだとアプリが永久に沈黙し、しかも理由が画面に出ない。
> 逃げ道として **30 分に 1 回だけ送ってみる**。
>
> `Credentials.IsExpired` / `Remaining` は**これで実際に使われるようになった**。
> `Fingerprint` は依然として未使用（ShortWatch 用）。

**ShortWatch（mtime を短間隔で見張る）は未実装。** 上の「送らない」で 429 の
実害は消えたので、残るのは復帰検知が最大 120 秒遅いことだけになり、
優先度は下がった。

```
401 → .credentials.json を強制再読込
  ├ トークンが前回と違う → 即リトライ（1 回）
  └ 同じ → ShortWatch モード（mtime を 2 秒間隔で最大 60 秒監視）
            変化 → 即リトライ
            60 秒で変化なし → AuthRequired 状態（間隔 300 秒へ）
```

`AuthRequired` 中も 300 秒ごとに再読込＋リトライを続けるので、**後から Claude Code を起動すれば自動復帰**する。

### 8-4. バックオフ

| 応答 | 扱い | 実装 |
|---|---|---|
| 401 | **バックオフに乗せる**（下記の変更理由） | ✅ |
| 403 | `NotAvailable`。5 回連続なら 1 時間間隔へ | ⬜ 現状は `Offline`（懸念 3） |
| 429 | **`Retry-After` を最優先で尊重**。無ければバックオフ。成功 3 回で戻す | ✅ |
| 5xx / タイムアウト | 30 → 60 → 120 → 240 → 480 → 600 秒（±20% ジッタ）。通常間隔より短い段は使わない | ✅ |
| JSON パース失敗 | 生ボディを `cache\last-error-body.txt` に保存（トークンは含まれないので安全） | ✅ |

> ### ⚠ `Retry-After` には 2 形式ある。両方読まないと「尊重した」ことにならない
>
> ```
> Retry-After: 120                             → 秒数。HttpClient は Delta に入れる
> Retry-After: Wed, 23 Sep 2026 20:00:00 GMT   → 絶対時刻。Date に入り Delta は null
> ```
>
> 当初 `Delta` しか読んでおらず、**日付形式が来ると黙って無視**していた。
> 「尊重する」と書いた直後に半分しか見ていなかったので、まさに
> 0 章の「対策したつもりを文書化しない」に自分で抵触した。
> ループバックのスタブで**両形式とも待つことを実測確認済み**。
>
> ジッタは `Retry-After` のときだけ **増やす側にしか振らない**。
> ±20% だと言われた時間より早く叩きうるため。
>
> ### ⚠ 401 をバックオフに乗せる（設計変更）
>
> 元は「401 はバックオフに乗せない」としていた。本体がトークンを更新すれば
> すぐ直るはずで、待つ意味が無いという理屈だった。
>
> **これが 429 の直接の原因だった。** 失効トークンを送らなくなった今、
> なお 401 が返るのは「失効以外の理由で拒否されている」＝ 待っても直るとは
> 限らない状況なので、回数を抑えるほうが正しい。
>
> ### ★ 送信間隔の下限は `UsageEndpointClient` で強制する
>
> 「60 秒未満では叩かない」は不変条件として書いてあったが、**守っていたのは
> `PollingService` の待ち時間計算だけ**だった。メニューの「今すぐ更新」は
> そこを通らないので、連打すれば連打しただけ飛んだ。
>
> `Log.Redact` と同じ考え方で、**唯一の出口である `FetchAsync` の中で強制する**。
> 前回送信から 60 秒経つまでその場で待つ。呼び出し側の作法に依存しない。

タイムアウトは `HttpClient.Timeout` ではなく `CancellationTokenSource(5s)` で制御する（`Timeout` は `TaskCanceledException` になって「ユーザーキャンセル」と区別できない）。

### 8-5. 状態とパネルの表示

パネルは文字数の制約が無いので、状態を**言葉でそのまま出せる**。
トレイ時代は 16px のアイコンで表現し分ける必要があったが、その工夫は不要になった。

| 状態 | 条件 | 表示 | 実装 |
|---|---|---|---|
| Starting | 起動直後 | `Claude 使用量  取得中…`（**空白にしない**。「起動してない」と誤解される） | ✅ |
| Ok | 最終成功 5 分以内 | 数値 + severity 色 | ✅ |
| Stale | 5〜15 分 | 末尾に `│ N分前` | △ UI 側で経過時間を見ているだけ。状態としては未使用（懸念 2） |
| Offline | 15 分超 / 連続失敗 | 末尾に `│ 接続できません` | ✅（判定条件は簡略） |
| AuthRequired | 401 が解決しない | 末尾に `│ Claude Code を起動してください` | ✅ |
| NotAvailable | `limits[]` 空 / 403 | 数値の代わりに `--` | △ `limits[]` 空のみ。403 は Offline に落ちている（懸念 3） |

**`Offline` と `AuthRequired` を分けているのが肝。** どちらも「取れない」だが、
前者は待つしかなく、後者はユーザーが Claude Code を起動すれば直る。
同じ表示にしてはいけない。

⚠ `rate_limits_available: false` になるケース（API キー利用 / Bedrock / Vertex / Foundry）がある。その場合はプランリミットの概念自体が無いので `NotAvailable` にフォールバックする。

以前は `PollingService` 1 つに全部入っていた。**可変フィールド 7 個、入口 2 本、413 行。**
429 を実機で出すまで誰も間隔の誤りに気づけなかったのは、間隔の判断が
取得処理・例外処理・状態発行と同じメソッドに混ざっていて、**単体で動かせなかった**から。

| | 持つもの | 依存 |
|---|---|---|
| `PollSchedule` | **いつ投げるか**だけ。バックオフ・`Retry-After`・成功 3 回での復帰 | **無し（純粋）**。時計も通信も要らずテストできる |
| `ISendGuard` | **投げてよいか**。止める理由と案内文をセットで返す | `Credentials` のみ |
| `PollingService` | 上の 2 つに従って投げ、結果を状態へ変換する | `Core` 内のみ |
| `WakeSignals` | OS のイベントを 1 本の起床シグナルに束ねる | `Platform`（OS 依存） |

**入口を 1 本にしたのが最大の変更。** 以前は定期ループと「今すぐ更新」が
別々の Task で走り、セマフォで衝突を防いでいた。衝突は防げても

- 手動の成功がループのバックオフを解除してしまう
- 手動が下限間隔の判断を素通りする

という「**片方にだけ効く穴**」が次々に出た。いまはループが 1 本で、
外からの要求は `Wake()` で**待機を打ち切るだけ**。取得は必ず同じ経路を通る。

> **`Core` は `Platform` を参照しない。** OS イベントの配線は
> `OverlayAppContext`（合成の場所）が行い、`PollingService` は受け口
> （`Wake`）だけを持つ。これで `Core` は UI にも OS にも依存しない。

未知の `kind` が来たとき enum だと 0 番に落ちて**別リミットと誤合算**する。`string` のまま保持し、分類は `switch` で行い、**未知 `kind` は捨てずに「その他」行として素通し表示**する。

## 11. JSONL 集計の実装方針

### 11-1. 探索と増分読み

```csharp
Directory.EnumerateFiles(projectsRoot, "*.jsonl", SearchOption.AllDirectories)  // 再帰必須（5-3）
    .Select(p => new FileInfo(p))
    .Where(f => f.LastWriteTimeUtc >= UtcNow - TimeSpan.FromDays(8));  // 週次 7 日 + 境界マージン
```

ファイルごとに `(Path, Offset, KnownLength, LastWriteTicks, LastRequestId)` を `ledger.json` に永続化。

### 全部読み直す条件（3 つ）

```
① キャッシュが無い / SchemaVersion が違う
② len < Offset                      切り詰め
③ mtime が巻き戻った                ★ 同サイズ以上での置き換え。
                                       サイズだけ見ていると取りこぼす
それ以外 → Offset..len を読む
```

③は既存実装が実際に踏んだもの。**サイズ比較だけでは不十分**。

### ★ 窓読み（一括バッファしない）

差分を一度に全部バッファすると、巨大なトランスクリプトでバイト配列＋文字列＋行配列が**数百 MB** になり UI がブロックする。**8MB ずつの窓**で進める。

```
・窓の境界にまたがる不完全な行は「バイト列のまま」持ち越す
  ★ 文字列にするとマルチバイト文字が割れて U+FFFD になり、バイト数も狂う（日本語パスで即死）
・処理しきれなかった末尾の分は Offset を巻き戻して次回読み直す
・末尾が '\n' で終わっていなければ最後の '\n' までしか処理しない
  （Claude Code は追記中なので最終行が途中で切れている可能性が常にある）
```

### ⚠ 短い読み取りを必ず考慮する

`stat` と `read` の間にファイルが切り詰められると、**要求バイト数より少なく読める**。

- ❌ `ReadExactly` — EOF で例外を投げる。追記中のファイルでは踏む
- ✅ `Read()` の**戻り値でスライスする**。バッファは `GC.AllocateUninitializedArray` ではなくゼロ初期化のものを使う（未初期化メモリをパースしないため）

`FileShare.ReadWrite | FileShare.Delete` で開き `Seek` → `Read` → `ReadOnlySpan<byte>` 上で `IndexOf((byte)'\n')` ループ。`StreamReader.ReadLine()` は使わない（オフセット管理が困難）。

**JSONL に `FileSystemWatcher` は使わない**（書き込み頻度が高くイベント嵐になる）。

> ✅ **検証方法（既存実装で実証済み）**: 窓サイズを **64KB に落として窓分割を強制**し、「全走査 / 増分 / 再全走査」の 3 通りで集計値が**完全に一致**することを確認する。窓境界のバグはこれをやらないと表に出ない。Phase 4 の必須テストに入れること。

### 11-2. パース

```csharp
if (line.IndexOf("\"usage\""u8) < 0) return null;               // ① バイト列で高速フィルタ
// （"type":"assistant" ではなく "usage" で弾く。巨大な attachment 行を JSON.parse せず素通りできる）
// ② Utf8JsonReader で必要フィールドのみ。iterations に来たら reader.Skip()
string key = requestId ?? messageId ?? uuid;                    // ③ 5-1 の対策
if (key == _lastRequestId) return null;                         //    重複は必ず連続して現れる
_lastRequestId = key;
if (model is null or "" or "<synthetic>") return null;
```

**`HashSet` は要らない**（5-1 参照）。重複は必ず連続して現れるので、**直前の `requestId` を 1 つ覚えるだけ**で排除できる。増分 tail と組み合わせるため、この「最後に見た `requestId`」をファイルカーソルと一緒に `ledger.json` へ永続化する。

`ledger.json` に `SchemaVersion` を持たせ、パーサを変えたらバージョンを上げて**全再計算**させる（集計ロジックのバグを引きずらない）。

> ⚠ **この簡略化は「重複は必ず連続」という実測（3 ファイル・非連続の重複 0 件）に依存している。** Phase 4 の検証で ccusage と ±5% 以内に収まらなかった場合は、まずここを `HashSet` 版に戻して切り分けること。

### 11-3. 更新タイミング

| タイマー | 間隔 | 対象 |
|---|---|---|
| 軽量 tail | **20 秒** | アクティブセッションの JSONL のみ（通常 1〜2 ファイル） |
| 全体スキャン | 120 秒 | 8 日窓（mtime フィルタで実際に読むのは変化分のみ） |
| 起動時 | 1 回 | `ledger.json` の差分。無ければフル走査（実測 1 秒未満） |

### 11-4. 永続キャッシュ

`%LOCALAPPDATA%\ClaudeUsageTray\cache\`:

| ファイル | 用途 |
|---|---|
| `last-usage.json` | 直近成功レスポンスの生 JSON。**起動直後に即アイコンを出す**（起動 → 空白数秒、を避ける）。スキーマ変更時の diff 用も兼ねる |
| `utilization-history.jsonl` | `{ts, session, weekly, scoped[]}`。予測用。8 日でローテート |
| `ledger.json` | JSONL 集計の中間状態 |
| `last-error-body.txt` | パース失敗時の生ボディ |

**書き込みは必ず atomic**（`WriteAllText(tmp)` → `File.Move(tmp, dst, overwrite: true)`）。読み込み側も try/catch で失敗したら黙って捨てて作り直す。

|---|---|---|

### R2 のフォールバック

**A（推奨・Phase 7）statusLine 経由** — Claude Code の statusLine は stdin で JSON を受け取り、その中に `rate_limits.{five_hour, seven_day, spend_limit}.{used_percentage, resets_at}` が含まれる（`used_percentage` は 0–100、`resets_at` は **Unix epoch 秒**。エンドポイント側の ISO8601 とは形式が違う点に注意）。**公式にサポートされた拡張ポイント**なので壊れにくい。

短所: **Claude Code が動いているときしか更新されない**（閉じている間は古い値のまま）。

> ### ✅ このフォールバックは既に半分できている（2026-09-21 判明）
>
> `~/.claude/settings.json` には**既に statusLine が設定済み**:
>
> ```json
> "statusLine": { "type": "command",
>   "command": "node %USERPROFILE%/.claude/statusline/statusline.mjs",
>   "padding": 0, "refreshInterval": 5 }
> ```
>
> 実装は [`claude-code-statusline.md`](../../ideas/work/claude-code-statusline.md) / `claude-code-statusline/statusline.mjs`。**5 秒ごとに実行され、ペイロードに `rate_limits` が来ているが現在は未使用**（同ドキュメントの「残っている検討事項」に明記されている）。
>
> → **ラッパーで包む必要はない。** 既存の `statusline.mjs` に「受け取った `rate_limits` をキャッシュファイルへ atomic 書き込みする」数行を足すだけでブリッジが完成する。ユーザーのステータスラインを壊すリスクもゼロ。
>
> ⚠ ただし **`refreshInterval: 5`（5 秒）でファイルが書かれる**ので、トレイ側は mtime を見て読むだけにし、`FileSystemWatcher` は使わないこと（イベント嵐になる）。

**B** JSONL からの P90 推定（ccusage / Claude-Code-Usage-Monitor 方式）。精度が低く分母がプラン・時期で変わるので「推定値」と明記して橙色表示。

### ★ 設計上の穴（対応方針を決める必要がある）

以下は判断の記録として残す。復活させるならここから。

旧 9-4 は `Shell_NotifyIcon` の `NIF_INFO`（バルーン）を前提にしていたが、
**トレイアイコンを廃止したので手段ごと消えた**。トリガ設計は有効なまま。

| 案 | 内容 | 評価 |
|---|---|---|
| A | **通知専用の隠し `NotifyIcon` を持つ** | 実装は最小。ただし「トレイを使わない」方針に逆行し、オーバーフローに 1 個増える |

「気づかせる」必要性はトレイ時代より低い。まず B で様子を見るのが妥当。

#### 懸念 2: `FetchStatus.Stale` が死んでいる（影響: 小 / Phase 2）

enum に定義したが**どこからも代入していない**。UI 側は独自に
「取得から 5 分以上経過」を見て `N分前` と出しているだけ。
状態の定義と実装が食い違っている。Phase 2 で `PollingService` 側に寄せる。

#### 懸念 3: 403 が `NotAvailable` に落ちない（影響: 小 / Phase 2）

401 以外の HTTP エラーが一律 `Offline` になっている。
API キー構成や Bedrock/Vertex では 403 が返り「リミットの概念が無い」のが
正しい状態なのに、「接続できません」と誤表示する。

#### 懸念 4: バックオフが無い → ✅ 2026-09-23 に対応（**実地での再発確認は未了**）

~~失敗しても 120 秒間隔で叩き続ける。`Retry-After` を無視する。~~

**対応済み**: 指数バックオフ（30→600 秒）、`Retry-After` の 2 形式対応、
成功 3 回での復帰、失効トークンの送信停止、送信間隔の下限強制。

> ⚠ **「直した」と言えるのはここまで。** スタブでの動作確認は済んでいるが、
> **本番のサーバー相手に 429 が再発しないことは、次の PC 再起動まで確認できない。**
> それまでは「対応した」であって「解決した」ではない。

以下は原因の記録として残す。

> ### ★ 429 には 2 種類ある。**暴走のほうはこちらが作っていた**
>
> 当初「429 は散発ではなくこちらが作っている」と書いたが、**言い過ぎだった**。
> 後の実測で、**有効なトークンでも単発の 429 が出る**ことを確認している（下の「3」）。
> 正しくは次の 2 つを分けて考える。
>
> | | きっかけ | 挙動 | 効く対策 |
> |---|---|---|---|
> | **暴走型** | 失効トークンの連投 | 401×3 → **429 が続く** | 失効なら送らない |
> | **単発型** | 不明（サーバー都合） | 429 が 1 回だけ。次で戻る | バックオフ |
>
> **どちらか一方の対策では足りない。** だから両方入れてある。
>
> #### 1 回目 — 2026-09-22 の PC 再起動直後
>
> ```
> 19:30:35  起動（startup=True）。PC 再起動で自動起動
> 19:30:51  401   ← トークンは PC の電源が落ちている間に失効済み
> 19:32:56  401   ← 本体が起動していないので誰も更新しない
> 19:35:00  401
> 19:37:04  429   ← ★ サーバーが 401 の繰り返しを見て 429 に切り替えた
> 19:39:08  429
> 19:40:57  429
> 19:42:53  429
> 19:43:31  ユーザーが claude を起動 → 19:43:36 にトークンが更新された
> 19:45:00  成功（自動復旧）
> ```
>
> #### 2 回目 — 2026-09-23 の朝（トークンが 03:43 に失効したあと）
>
> ```
> 09:01:56  401
> 09:03:46  401
> 09:05:38  401
> 09:07:32  429   ← ★ 1 回目と同じく、401 が 3 回続いた直後
> 09:09:43  429
> 09:11:37  429
> 09:13:39  429
> ```
>
> **2 回とも「401 が 3 回 → 4 回目から 429」で一致した。** 偶然では説明が付きにくく、
> **失効トークンの連投が暴走型の 429 を招いている**と考えてよい。
>
> ただし、サーバー側の正確な規則（3 回なのか、時間窓なのか、401 専用なのか）は
> 外からは分からない。**確定しているのは「こちらが連投をやめれば起きない」までで、
> 「サーバーがこう判定している」は推定である。**
>
> → **検証は次の PC 再起動。** 失効状態で 429 が出なければ対処が効いている。
>
> #### 3 回目の観測 — 2026-09-23 10:59。**単発型が実在する**
>
> 修正後のビルドを本番エンドポイントに向けて 1 時間動かした結果:
>
> ```
> 10:00:00  起動（120 秒間隔）
>   … 約 30 回の取得が成功。401 は 1 度も無い …
> 10:59:38  429   ← ★ 有効なトークンで、単発で発生
> ```
>
> **401 を 1 度も挟まずに 429 が来た。** つまり 429 は失効の連投だけが原因ではない。
> 当初の「429 はこちらが作っている」という断定は誤りで、**暴走型の説明にすぎなかった**。
>
> 単発型はバックオフで受け止めるしかない（1 回失敗しても次で戻る）。
> **失効ガードだけでは足りず、バックオフだけでも足りない。**
>
> **これは「行儀が悪い」の域を超えている。** PC を再起動してから Claude Code を
> 起動するまでの間、毎回この状態になる。ユーザーの操作が遅いほど長く叩き続ける。
>
> #### おまけ: ネットワーク断でも同じことが起きていた
>
> 2026-09-23 の 01:15〜09:00、DNS が引けない状態が続いた。バックオフが無いため
> **8 時間で 233 回**「そのようなホストは不明です」を記録している。
> 429 とは別経路だが、「失敗しても間隔を変えない」という同じ欠陥が原因。

#### 懸念 5: 401 後の復帰が遅い → △ 2026-09-23 に主因を除去。ShortWatch は残件

**除去した主因**: 失効トークンを送らなくなった（8-3）。これが懸念 4 の 429 を
招いていた部分。`Credentials.IsExpired` / `Remaining` はここで使われるようになった。

**残件**: ShortWatch（mtime の短間隔監視）は未実装なので、本体がトークンを
更新してから画面が戻るまで最大 120 秒かかる。`Fingerprint` は依然未使用。
**影響は「表示が少し遅い」だけになったので、優先度は下げてよい。**

#### 懸念 5-b: 429 が `AuthRequired` の案内を握り潰す → ✅ 2026-09-23 に対応

事故当時、パネルの表示はこう変わっていた:

| 時刻 | 状態 | 表示 |
|---|---|---|
| 19:30〜19:35 | `AuthRequired` | `Claude Code を起動してください` ← **正しい案内** |
| 19:37〜19:42 | `Offline` | `接続できません` ← **嘘。ユーザーにできることが消えた** |

429 が `Offline` に落ちるため、**直前まで出ていた行動可能な案内が、
何もできないメッセージで上書きされていた**。`Offline` と `AuthRequired` を
分けた意味（8-5）が失われていた。

**対応**: `PollingService.TransientFailure()` が、現在 `AuthRequired` なら
状態を維持する。

> ⚠ **逆向きの誤案内が残っている（未対応）。**
> 認証が直ったあとにネットワークが落ちると、原因はネットワークなのに
> `AuthRequired` を保ち続け「Claude Code を起動してください」と出す。
> 維持する回数にも時間にも上限を置いていない。
> 懸念 8（本体プロセスの検出）を入れれば自然に解けるので、そこまで保留する。

#### 懸念 6: 非公開 API 依存のまま、フォールバックが未実装（影響: 大 / Phase 7）

エンドポイントが消えたら**「接続できません」と出続けるだけ**になる。
14 章に撤退ラインは書いてあるが、実装はまだ無い。
statusLine 経由（フォールバック A）は既存の `statusline.mjs` に数行足すだけで
足場ができるので、コストは低い。

#### 懸念 7: 完了ダイアログが表示されない（影響: 小 / **原因を一部特定**）

`--install` / `--uninstall` の `MessageBox.Show` が**表示されないまま戻る**。

> ### ★ 2026-09-23 に分かったこと: **ウィンドウは作られている**
>
> 長く「ダイアログが生成されていない」と扱っていたが、**誤りだった**。
> 残っていたインストーラのプロセスを調べたところ:
>
> ```
> MainWindowHandle : 726980
> MainWindowTitle  : "ClaudeUsageTray"
> Responding       : True
> 経過             : 136 秒（応答待ちで止まっていた）
> ```
>
> **「出ない」のではなく「見えない場所で応答を待っている」。**
> だからインストーラのプロセスが終わらないことがあった
> （終了コード 0 で 3.2 秒、という以前の観測とは挙動が割れる）。
>
> 非対話的な文脈から起動すると Windows が前景化を拒む、いわゆる
> 前景ロックに合致する。
>
> ### ⚠ 試した対策は 2 つとも失敗した。**入れていない**
>
> | 試したこと | 結果 |
> |---|---|
> | 最前面の所有者 `Form` を作って `MessageBox.Show(owner, …)` | ダイアログが**一度も出なくなった**。ブロックもしない |
> | 所有者の位置を `-32000`（最小化の特別値）から画面内＋`Opacity=0` へ | 変化なし |
>
> どちらも改善を確認できなかったので**差し戻した**。
> 直す前より悪くなっていない保証が取れないものは入れない（0 章）。
>
> **次に触る人へ**: 出発点は「ウィンドウは実在する」という事実。
> 前景化の問題として攻めるのが筋で、`AllowSetForegroundWindow` や
> `SetForegroundWindow` の明示呼び出し、あるいは**ダイアログをやめて
> パネル側に結果を出す**のが候補。検証は**対話的なシェルから手で叩く**こと
> （エージェント経由の起動では前景権の条件が変わり、判定を誤る）。

**機能自体は全て正しく動く。フィードバックが無いだけ。**
ただしユーザーは `--uninstall` を叩いても何の反応も得られないので、
「効かなかった」と誤解する。UX として要改善。

#### 懸念 8: 本体プロセスの有無を見ていない → ✅ 2026-09-23 に対応

**トークンを更新できるのは Claude Code 本体だけ**なので、`claude` プロセスが
1 つも無ければトークンは絶対に更新されない。これは端末の時計にも `expiresAt` にも
依存しない、確実な判断材料になる。

> ### ★ 実装してみて、いちばん大事だったのは「止めないこと」だった
>
> 着手前は「本体が動いていない ＝ 使用量は動かない ＝ 取りに行かなくていい」と
> 書いていた。**これは誤り。** 週次リミットは**アカウント単位**なので、
> **別の端末や claude.ai の利用でも数字は動く**。
>
> 手元で本体を閉じている間に取得を止めると、「PC で Claude Code を閉じている間
> だけ週次が更新されない」という、原因のきわめて分かりにくい不具合になる。
>
> → **間隔を伸ばすだけ**にした（120 秒 → 600 秒）。`PollSchedule.Idle`。

**実装したこと**（`Core/ClaudeProcess.cs`）:

- 判定は `~/.claude/sessions/<pid>.json` の `pid` が生きているかで行う。
  **プロセス名では見ない**（`claude` という名前は他にもあり得る）。
  本体が自分で名乗っている情報を正とする
- 12 時間より古い session ファイルは無視する。本体が落ちるとファイルは残るので、
  pid の生存だけだと**別プロセスによる pid 再利用**で誤判定しうる
- 20 秒キャッシュ。毎ポーリングで数ファイル読む程度だが、連続呼び出しは束ねる
- **判定に失敗したら「動いている」と答える。** 分からないときに「動いていない」と
  答えると、間隔が伸びて失効ガードも強く効いてしまう。
  **安全側は「従来どおりの挙動」のほう。**

**解けたもの**:

- **失効判定の裏取り** — 本体が動いていないなら、時計を疑うプローブは不要。
  更新できる者が居ないのだから失効しているのが当然（8-3）
- **8-1 の「本体が 1 つも起動していない → 600 秒」**

**解けなかったもの**: 懸念 5-b の逆向き誤案内。「本体が動いている＝認証は生きている」
とは限らない（サインアウト状態でも本体は動く）ので、これだけでは言い切れない。

## 19. セキュリティ

このアプリは **アクセストークンを読む** という性質上、扱いを間違えると被害が大きい。
設計上どう守っているかと、残っているリスクを明記する。

### 19-1. 何を読み、何を書くか

| 対象 | 読 | 書 | 備考 |
|---|---|---|---|
| `~/.claude/.credentials.json` | ✅ | **❌** | 読むだけ。ロックもしない（4-3） |
| `~/.claude/sessions/*.json` | ✅ | ❌ | User-Agent のバージョン追従用 |
| `%LOCALAPPDATA%\ClaudeUsageTray\` | ✅ | ✅ | 自分のデータだけ |
| `HKCU\...\Run` | ✅ | ✅ | 自動起動の登録のみ。**昇格しない** |

**`~/.claude` には一切書き込まない。** 本体のデータを壊さないための原則。

### 19-2. トークンの扱い

| 守ること | どうやって |
|---|---|
| 保持しない | `PollingService` はフィールドに持たず、ローカル変数としてのみ扱う。同一性の比較は `SHA256` の先頭 8 バイトだけ |
| 常駐オブジェクトに残さない | `HttpClient.DefaultRequestHeaders` には入れず、`HttpRequestMessage` に毎回セットする |
| ログに出さない | `Log.Write` の内部で `Redact()` を**強制適用**。40 文字以上の `[A-Za-z0-9_-]` 列をまとめて伏せる。呼び出し側の意識に依存させない |
| 例外から漏らさない | `ex.ToString()` を出さない。型名と 200 文字までのメッセージのみ。スタックトレースも残さない |
| ディスクに書かない | キャッシュに保存するのは**レスポンスボディだけ**。リクエストヘッダは保存しない |

### 19-3. ★ 送信先の制限

**取得先はトークンを Bearer で送る相手**になる。`--endpoint` を無制限に許すと、
ショートカットや Run キーを書き換えるだけで「トークンを任意のサーバへ送らせる」
ことができてしまう。平文 `http` なら経路上でも読める。

> ⚠ **「https なら許す」では対策にならない。** 攻撃者は自分のサーバに証明書を
> 用意できるので、`https://evil.example.com/` を指定すればそのまま盗める。
> **TLS は経路を守るだけで、送り先が正しいことは保証しない。**
> 一度この誤りを入れて、レビューで指摘された。

許すのは次の 2 つだけ。それ以外は黙って既定値に戻す。

- **既定の取得先と同じホスト宛ての `https`**（＝ `api.anthropic.com`）。
  パスやクエリの差し替えは許す
- **ループバック宛て**（検証用スタブ。経路が端末内で閉じるので `http` でも可）

### 19-4. ディスクに残るもの

| ファイル | 中身 | 機微度 |
|---|---|---|
| `cache\last-usage.json` | 使用量レスポンスの生 JSON | 低。消費率・リセット時刻・追加クレジット枠。**トークンは含まれない** |
| `cache\last-error-body.txt` | 失敗時のレスポンスボディ | 低。同上 |
| `logs\tray.log` | 動作ログ | 低。`Redact()` 済み |
| `settings.json` | 表示位置など | なし |

いずれも `%LOCALAPPDATA%` 配下でユーザースコープ。暗号化はしていない。
**アカウントの使用状況が分かる程度の情報は平文で残る**点は把握しておくこと。

### 19-5. 権限

- **昇格しない。** 書き込むレジストリは HKCU のみ
- 他プロセスを操作するのは `StopOtherInstances()` だけで、対象は
  プロセス名が `ClaudeUsageTray` のものに限る
- ネットワークは HTTPS の GET 1 本のみ。受信データはパースするだけで実行しない

### 19-6. 残っているリスク

| # | リスク | 評価 |
|---|---|---|
| 1 | **コード署名なし** | SmartScreen / Defender に警告される可能性がある。個人用途では許容 |
| 2 | **同名プロセスの巻き添え** | `StopOtherInstances()` はプロセス名だけで判定する。無関係な同名プロセスがあれば止めてしまう。実用上は問題にならない |
| 3 | **`Installer` がディレクトリを丸ごとコピーする** | 信頼できない場所から `--install` すると、その中身ごと配置先へ複製される。自分でビルドしたものを使う前提 |
| 4 | **キャッシュが平文** | 19-4 のとおり。端末が他人に渡る前提なら別途保護が要る |
| 5 | **非公開 API への依存** | セキュリティというより可用性の問題（14 章 R2） |

### 19-7. 公開リポジトリとしての注意

- **コミットの author / committer は GitHub の noreply アドレス**にしてある
- ドキュメント内のローカルパスは `%USERPROFILE%` 等の一般表記に置換済み
- `bin/` `obj/` `publish/` は `.gitignore` 済み。ビルド成果物には絶対パスが
  埋め込まれるため、**追跡対象に入れないこと**
